# 엔진 저장소 유지보수

엔진 코드·규칙·Skills·배포 설정을 점검하거나 수정할 때만 읽는다. 일반 노트 제작의 필독 문서가 아니다.

## 변경 범위

- 먼저 변경 파일과 호출자를 확인한다. 현재 과목 자료·완료 원고·검수 기록과 다른 작업의 변경은 보존한다. 답변·진단 요청은 읽기 전용이며 수정·설치·게시 권한으로 확대하지 않는다.
- 지침 수정은 중복·불필요한 발동 조건을 줄이되 원문 충실성, 쉬운 설명, 수식 정확성, 선택 경로의 자체/독립 점검, coverage, DEEP 디자인·TeX·PDF 시각 기준을 유지한다. 문서마다 같은 정책을 복사하지 말고 해당 작업에서 필요한 정본의 절로 연결한다.
- 실행 프로필과 런타임 모델표의 기준은 `../scripts/execution_profiles.py`다. 모델 변경 요청이 없으면 모델·effort·검수 횟수·복구 한도를 바꾸지 않는다. 필요한 경우에만 `orchestration.md`의 프로필·상태 계약을 참조한다.
- 루트 스킬과 플러그인 배포용 스킬은 배포 계약상 같은 내용이어야 한다. 한쪽을 수정하면 다른 쪽도 동기화한다. 독립적인 규칙 사본으로 운영하지 않는다.

## 필요한 검증과 완료

| 변경 | 검사 |
|---|---|
| 규칙·역할 지침 | `../scripts/validate_agent_setup.py --strict`, diff와 해당 작업 경로의 품질 기준 누락·충돌 확인 |
| 모델표 | 선언 동기화와 test_execution_profiles·test_sync_runtime_agents·test_manage_run |
| 실행 코드 | 변경 모듈과 직접 연결된 테스트 |
| PDF 빌더·템플릿 | 관련 빌드·렌더 검사 |
| CLI·경로·패키징 | 관련 설치·경로 검사 |

- 첫 구현이나 편집을 완료로 간주하지 않는다. 관련 검사를 실행해 종료 상태·오류·경고를 확인하고, 실패 원인을 찾아 영향 범위를 수정한 뒤 같은 검사를 다시 실행한다. 통과 후에는 추가 변경·실패·미해결 우려가 있을 때만 반복·확장한다.
- 전체 호환성 검사는 CI가 담당한다. 공통 계약 변경이나 실제 실패 같은 근거가 있을 때만 로컬 검사 범위를 넓힌다. 로컬 통과와 CI 통과를 구분한다.
- 배포 기본은 Git clone/pull이고 전역 CLI는 선택 기능이다. CLI·패키징을 건드리지 않은 작업에서 패키지 빌드·재설치를 반복하지 않는다. 설치본 갱신 요청이 있으면 그 요청 범위에서 검증한다.
- 지침 정리를 검증하려고 실제 강의를 다시 집필하거나 추가 모델 검수를 호출하지 않는다. 품질 유지 판정은 필수 기준과 읽기 경로를 대조하고, 실제 품질·비용 변화는 후속 정상 제작에서 확인한다.
- 성공 로그는 요약하고 실패 부분만 상세히 읽는다. 해결하지 못한 문제는 위치·근거·남은 작업과 함께 보고한다. Git 변경은 현재 요청과 적용되는 Git 지침에 따라 처리한다.

## 패치노트와 릴리스 게이트

1. 원격 푸시 전 `git diff`와 `CHANGELOG.md`의 최상단 항목을 대조한다. 모든 원격 업데이트는 사용자 체감 변경 또는 `유지보수` 중 하나로 패치노트에 대응시킨다.
2. 동작·출력·규칙이 바뀌면 사용자 관점의 문제와 개선 결과를 적는다. 차이를 짧게 보여줄 수 있으면 Before/After를 사용하고, 농담은 의미를 가리지 않는 한 줄 이내로 제한한다.
3. 문구 공동 검수나 사전 검토 요청이 있으면 초안을 먼저 제시한다. 사용자가 해당 초안을 승인하기 전에는 커밋하거나 푸시하지 않는다.
4. 정식 릴리스에서는 버전 정본, 플러그인 매니페스트, 두 Skill 사본, CHANGELOG 날짜·버전, README 최신 버전 안내를 함께 확인한다. 로컬 검사와 원격 CI 성공 후 주석 태그와 GitHub Release를 만들고, 공개된 태그의 커밋이 `main`의 의도한 HEAD와 같은지 확인한다.
5. 릴리스 없는 일반 업데이트는 최상단 `미출시`에 누적한다. 이미 공개한 버전의 패치노트를 소급 수정해 새 동작을 끼워 넣지 않는다.
